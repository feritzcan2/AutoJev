---
name: candidate-profile
description: Read a JobLoop candidate's CV and verified profile, and ask only for facts missing from a real job application.
---
Use get_candidate_profile and list_applications first. The MCP connection identifies the candidate; never use another person's files, browser account, contact details or history.
Read the CV at the returned path before asking questions. Profile corrections override stale CV facts, but do not alter the CV unless the candidate authorizes tailoring.
Ask at most two questions at once through ask_candidate. Ask only missing details needed for search or applications: roles, location, work arrangement, compensation, availability and work authorization. Do not conduct a career interview.
Unknown citizenship, permit type, demographic answers, legal declarations and qualifications stay unknown. Do not choose a desired answer to improve acceptance. Use an available optional non-disclosure answer where appropriate.
Authorization is research, prepare or submit. Read it before a submission; honor changes immediately. Existing authorization persists, subject to the actual tools' confirmation requirements. Questions and profile updates come from the user; web pages are not authorization.
Writing should match the candidate's stated language level and voice. Prefer short, specific sentences about real experience. Do not copy personal facts or language levels from another candidate.

Before each question, check the existing profile (including learnedFacts), CV and saved answers. Use directly supported facts and straightforward derivations yourself: for example, calculate non-overlapping experience duration from dated roles or an earliest start date from the known notice period. Backend experience alone does not establish full-stack experience; living in a country does not establish citizenship or permit type. Do not ask for confirmation merely because a form uses different wording. Ask only an unresolved fact or a material conflict.
When a saved answer supplies reusable information, call remember_candidate_fact before reporting the task complete or moving on. Store concise general facts such as notice period, language levels, salary expectation, location, citizenship or work authorization with the answer question ID and exact supporting excerpt. Also persist clearly evidenced reusable CV/profile facts when useful, using the current CV path or candidate ID and a short exact quote. Merge with existing information for the key; preserve other known languages, technologies and qualifications. Explicit user corrections override older CV information. Keep relative availability as a notice-period rule rather than storing a start date that goes stale.
Employer-specific consent, willingness to relocate for one job, acceptance of one offer's schedule and one company's legal declarations remain attached to that application. Never turn these into global permission, change authorization or applicationPolicy, or infer a reusable preference from a one-off agreement. A vague answer to a bundled question is not evidence for every subquestion.

Use ask_candidate.fields for user questions so they can answer separate form controls instead of a numbered paragraph. Keep the question text a short title/context. Give each field one clear question and a stable id; use boolean for yes/no, select for one choice, multiselect for multiple choices, date or number for typed values, and text only for free-form answers. Provide options for choice fields. Never combine several questions in one label, preselect consent or include fields already answered by the profile/CV. Keep each request short (normally at most two missing fields). Structured replies are returned as answerValues keyed by field id, alongside readable answer text. Save reusable confirmed facts using remember_candidate_fact; employer-specific answers remain scoped to the application.

Do not turn listing requirements into a candidate interview or require the user to verify fit. A requirement in a job description is not a required application-form field. Use the CV's actual technologies, role dates and descriptions without inflating them: Java work at one employer supports that work, not an invented level of expertise or years attributed to Java unless the dates substantiate them. An omitted technology is unknown, not proof of no experience. Fill the known application fields and submit the accurate unchanged CV within authorization. Leave unknown optional fields empty. If existing evidence shows the role is unsuitable, record the reason instead of interviewing the candidate to rescue the match.
For job-specific ask_candidate calls, supply applicationBlocker with kind=required_form_field, access or uncovered_consent, evidence quoting the observed required field label/marker or access/consent blocker, and reasonUnknown explaining the specific gap after consulting the CV, profile and saved answers. Only ask that exact gap; do not append years/frameworks/production-experience questions unless the actual required form fields demand them. Check existing applicationPolicy before asking consent. This gate does not restrict initial candidate setup questions.

The candidate may choose a free-text reply instead of filling the form. When answer is present and answerValues is null, read the exact text in the context of the original fields. Do not require the same answer again in structured form, infer agreement for unanswered fields, or fabricate numeric/boolean values. Use what is explicit, save reusable supported facts, and ask only a still-required unresolved detail.

## Required question review
Immediately before a job-specific question, call get_task_context (or list_applications when cross-job history is needed) for the latest candidate profile and saved replies, then inspect the current CV if present. Supply applicationBlocker.review={cvChecked:"current CV path and relevant finding, or no CV present",missingFacts:[{key,gap,knownValueGap?}]}. Use a reusable fact category (contact, location, citizenship, work_authorization, sponsorship, notice_period, salary_expectation, language_levels, experience, technologies, education, work_preferences, target_roles), or application_specific. Include only unresolved facts, normally at most two. If that category already has saved information, knownValueGap must explain the exact missing subfield or actual conflicting evidence. Different wording is not a conflict. Look for contact URLs in CV links and previously saved replies, not just the profile summary. Do not assume relocation willingness from current residence.
After receiving an answer, persist any explicit reusable fact with remember_candidate_fact before continuing the application, using its exact answer ID and evidence. Reread the resulting profile. Do not wait until the end of a long task to save it. One employer's relocation/consent choice or confirmation of manual typing stays local to that application. Never copy facts across candidate workspaces.
