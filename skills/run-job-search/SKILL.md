name: run-job-search
description: Run and resume a JobLoop search campaign, coordinate the search and application skills, handle answers and keep the app current.
---
Read only the skill relevant to the current task when its contents are not already in context. Use get_task_context for fresh task data; do not reread all skills or full history on every turn. JobLoop MCP is the durable authority; no parallel spreadsheets or personal notes. The profile, authorization and history belong only to the candidate bound to this MCP connection.
At session start read get_task_context once and inspect its assigned job, relevant questions and compact unfinished-tab checkpoints. Request full history only when an actual cross-job check requires it. Recover an interrupted submission by inspecting external confirmation first. Never restart an uncertain application. If ownership belongs to an old session, ask the user to reclaim it in the app.
Work to the user's stopping condition, using a repeated search → assess → record → apply → verify cycle. Count only submitted records with observed evidence; prepared or uncertain records do not count. Stop for a real blocker, exhausted suitable current opportunities, revoked authorization, or the user's stop request. Do not keep generating empty status updates.
In browserMode=existing, use Codex’s native Chrome tools and the existing ChatGPT/Codex Chrome extension. Read the actual tool instructions first; available tools may be exposed as cua_repl or node_repl. JobLoop does not expose Playwright tools in this mode. A separate profile is used only when the candidate explicitly selects browserMode=separate. Verify the signed-in account belongs to the candidate before filling or submitting. If native tools are missing, report the missing Codex browser capability accurately. Never ask for Playwright installation or switch browser providers on your own. Only browserMode=separate uses JobLoop browser_* tools. Login/MFA requiring personal credentials needs the user. For CAPTCHA, first check whether automatic verification clears and attempt the normal visible challenge if the active browser tool permits and supports it (at most two attempts and 60 seconds total). Verify the outcome; ask through ask_candidate with recovery.kind=captcha only for a still-required challenge or a specific tool restriction/missing capability. Follow the CAPTCHA recovery procedure in apply-to-jobs; never evade a tool restriction. Continue other possible work while waiting. Never copy another person's cookies or credentials.
Keep each unfinished application in its own tab and persist its resumeContext before leaving it. Never reuse a waiting application's tab for searches or other jobs. When an answer is saved, finish the currently assigned bounded task; the scheduler prioritizes that application's continuation next. Reacquire its saved tab and inspect its current page before continuing. After ask_candidate, do not repeatedly ask the same question. Refresh get_task_context for relevant answers; a user answer notification is a cue to read the saved answer and continue. Existing authorization remains valid within its recorded scope and the tool's own rules.
Report concise status changes as work happens, including the reason a listing was skipped or blocked. Do not interpret heartbeat or hook events as evidence that an application succeeded.

## App-managed campaigns
Read get_task_context once at the start of every assigned task; its campaign and setup fields replace separate get_campaign and list_applications checks. When a running campaign supplies a task ID, execute only that bounded task. Report its outcome with report_campaign_work using that exact task ID before ending the turn, except when record_submission returned completion.taskReported=true: the task is already durably reported, so end the turn without another report or status update. The desktop scheduler owns the configured source, per-source rescan timer and application mode; do not launch a parallel endless loop, switch sources, sleep in a tool, or invent your own task ID. Use done for a completed batch or processed application, no_results for a completed search with no new suitable listings, and blocked for a missing capability or user information. Continue to use record_submission exclusively for actual submission proof. A prepared application is not a submitted one. If no campaign is active, follow the explicit user request.

## Visible progress
Use report_activity at the start of each task and when moving to a different concrete step. Include the jobId when working on a listing. Use a short user-facing sentence such as “Checking the employer listing”, “Filling the application form”, or “Waiting for your answer about the start date”, in the candidate's language. Report only actions actually underway; do not expose private reasoning or invent progress. No periodic heartbeat messages or repeated pre-submit announcements. Application state transitions already communicate preparing/submitting, and record_submission communicates the saved result. Continue using application state tools and record_submission for authoritative outcomes.

Automatic application mode is standing candidate authorization, not a request for another confirmation: if the current profile authorizes submit and the source allows auto, submit the completed accurate application without asking “Do you approve this application?” or creating an approval form. Re-read settings before submission and honor revocation, prepare/research modes, provider-required approvals and uncertain-submission verification. Use existing privacy/group-recruitment permissions without asking again. Uncovered consent questions must include applicationBlocker.consentScope; never disguise routine submission approval as an unknown form fact. Prompts describe the application's saved authority; do not impersonate the candidate or invent new first-person instructions.

Before ending each browser turn (including searches), preserve every still-needed unfinished application tab, not just the current tab: refresh markHandoff() for those tabs when supported. Retention marks are turn-scoped; otherwise an unrelated search turn can close forms awaiting user answers. Keep the saved browser identity and checkpoint current. A missing tab must be recovered and verified by the agent before asking the user to type into it.

## Task context and phase
Use get_task_context at the beginning of each assigned task. Verify setup is complete (or absent for a legacy profile), campaign status is running and the task ID matches the command. A matching app task is a user-authorized scheduler instruction; completed onboarding ends earlier setup-only restrictions. If state does not match, do not act externally. Current profile preferences override geographic examples in source settings; never silently broaden the candidate's constraints.

## Completion and recovery
Call report_campaign_work before ending every assigned task. For applications, done requires recorded submission proof, a skipped reason, or prepared only when submission is not authorized. A user-dependent blocker requires a job-linked ask_candidate question and blocked job status. Technical blockers requiring no user answer require blocked/uncertain status and blocker={kind:technical,requiresUserInput:false,evidence,reason}. Never disguise approval as technical failure. If reporting is rejected, complete the missing requirement on the same task.

A continuation command resumes the SAME task. First read current task context and the latest user messages; honor an explicit user stop request and report blocked instead of external actions. Inspect existing tabs and submission evidence. Already submitted/skipped jobs need only an outcome report; never resubmit. Unanswered required questions remain blockers. When recoveryQuestionId is present, inspect that technical question, recover its exact draft, save the checkpoint and recheck visible fields (AX/DOM can redact values). If resolved or misleading, use resolve_technical_question with observed evidence, never fabricated answers or consent.
