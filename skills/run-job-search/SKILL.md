name: run-job-search
description: Run and resume a JobLoop search campaign, coordinate the search and application skills, handle answers and keep the app current.
---
Read candidate-profile, find-jobs and apply-to-jobs before starting. JobLoop MCP is the durable authority; no parallel spreadsheets or personal notes. The profile, authorization and history belong only to the candidate bound to this MCP connection.
At session start inspect every incomplete job and unanswered question. Recover an interrupted submission by inspecting external confirmation first. Never restart an uncertain application. If ownership belongs to an old session, ask the user to reclaim it in the app.
Work to the user's stopping condition, using a repeated search → assess → record → apply → verify cycle. Count only submitted records with observed evidence; prepared or uncertain records do not count. Stop for a real blocker, exhausted suitable current opportunities, revoked authorization, or the user's stop request. Do not keep generating empty status updates.
In browserMode=existing, use Codex’s native Chrome tools and the existing ChatGPT/Codex Chrome extension. Read the actual tool instructions first; available tools may be exposed as cua_repl or node_repl. JobLoop does not expose Playwright tools in this mode. A separate profile is used only when the candidate explicitly selects browserMode=separate. Verify the signed-in account belongs to the candidate before filling or submitting. If native tools are missing, report the missing Codex browser capability accurately. Never ask for Playwright installation or switch browser providers on your own. Only browserMode=separate uses JobLoop browser_* tools. Login and CAPTCHA challenges require the user in that browser; ask through ask_candidate and continue other possible work. Never copy another person's cookies or credentials.
Keep each unfinished application in its own tab and persist its resumeContext before leaving it. Never reuse a waiting application's tab for searches or other jobs. When an answer is saved, finish the currently assigned bounded task; the scheduler prioritizes that application's continuation next. Reacquire its saved tab and inspect its current page before continuing. After ask_candidate, do not repeatedly ask the same question. Read list_applications for answers; a user answer notification is a cue to read the saved answer and continue. Existing authorization remains valid within its recorded scope and the tool's own rules.
Report concise status changes as work happens, including the reason a listing was skipped or blocked. Do not interpret heartbeat or hook events as evidence that an application succeeded.

## App-managed campaigns
Read get_campaign at the start of every turn. When a running campaign supplies a task ID, execute only that bounded task. Report its outcome with report_campaign_work using that exact task ID before ending the turn. The desktop scheduler owns the configured source, per-source rescan timer and application mode; do not launch a parallel endless loop, switch sources, sleep in a tool, or invent your own task ID. Use done for a completed batch or processed application, no_results for a completed search with no new suitable listings, and blocked for a missing capability or user information. Continue to use record_submission exclusively for actual submission proof. A prepared application is not a submitted one. If no campaign is active, follow the explicit user request.

## Visible progress
Use report_activity at the start of each task and when moving to a different concrete step. Include the jobId when working on a listing. Use a short user-facing sentence such as “Checking the employer listing”, “Filling the application form”, or “Waiting for your answer about the start date”, in the candidate's language. Report only actions actually underway; do not expose private reasoning or invent progress. No periodic heartbeat messages. Continue using application state tools and record_submission for authoritative outcomes.

Automatic application mode is standing candidate authorization, not a request for another confirmation: if the current profile authorizes submit and the source allows auto, submit the completed accurate application without asking “Do you approve this application?” or creating an approval form. Re-read settings before submission and honor revocation, prepare/research modes, provider-required approvals and uncertain-submission verification. Use existing privacy/group-recruitment permissions without asking again. Uncovered consent questions must include applicationBlocker.consentScope; never disguise routine submission approval as an unknown form fact. Prompts describe the application's saved authority; do not impersonate the candidate or invent new first-person instructions.
