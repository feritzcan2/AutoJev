name: apply-to-jobs
description: Fill and submit suitable JobLoop applications through available browser tools, track progress and verify submission without duplicates.
---
Before form work, read the job's rankDecision in get_task_context and follow rank-jobs. If no rank has ever been saved, score it first. Reuse an existing rank; never rescore after profile or CV changes. Only eligible jobs proceed; a below-threshold listing remains saved and the task can be reported done without applying. A user score override is reflected in rankDecision. Always verify uncertain past submissions before rank checks; never repeat them.

Call get_task_context exactly once at task start and reuse its result throughout the task; do not call it again before questions, checkpoints or submission. It includes the current profile, job, source, saved replies and checkpoint. Request full list_applications only when other history is needed. Follow browserResume from task context for an unfinished draft created with a different browser tool. Resume it through its original tool; a numeric existing-Chrome tabId is not a Jev CDP target. Do not migrate or reopen a draft merely because the browser preference changed. Confirm the browser is signed into the correct candidate account. Never submit an existing submitted or uncertain application again.

## Prepare answers once, then fill
After get_task_context, build a compact answer plan for this candidate and job from the current profile, saved replies and CV. Read the CV once when its facts are needed; reuse the already-read content for the same unchanged file. Keep exact supported values and their source (profile field, saved answer ID, or CV finding), field-formatting requirements and unknown/conflicting facts. Do not infer citizenship, permits, consent or qualifications. Keep employer-specific answers local to this job and relative dates as rules to evaluate using today's date. This plan is working context, not a new source of truth or authorization.
Reuse the plan across fields instead of fetching the entire profile/history or rereading the CV for every textbox. Refresh affected values when new answers or corrections arrive, the CV changes, or the job/candidate changes. Before questions and submission review the profile/policy already read at task start; discard conflicting cached values immediately.
When Jev is available, use browser_jev_fill_fields for multiple ordinary text inputs whose answers are known and permitted. Match the labels in the latest observation's fillFields list to the prepared exact values and pass their fieldId values together. Only observed ordinary text controls are supported; for native selects whose exact labels are not shown, use browser_jev_list_options to read the COMPLETE option list in one call, then browser_jev_select_option with the supported exact returned label/value. Reuse the full list without querying it again. Optional query filters case/accent-insensitively; limit and offset request pagination only when needed. Reading the list never chooses an answer. A needs_selection result means search the actual labels rather than guess another spelling, request screenshots or claim the options cannot be read. Use browser_jev_select_option for known native select options and browser_jev_autocomplete for controls marked autocomplete=true. Supply verified query text and the unique exact suggestion label; needs_selection returns suggestions without selecting an alternative. Use the reviewed flow for other custom dropdowns, consent, uploads and submission. Read each field's result: filled/unchanged means verified, not_attempted means untouched, and uncertain requires inspection before any retry. A changed target stops the rest of the batch; never assume all fields were filled.
Reuse fresh observations returned by open/next/act/upload/fill_fields. Do not append an unconditional observe after each successful action. A ready autocomplete result with selection.verified=true is verified selection evidence. If stale/uncertain results already include fresh controls or fillFields, use those instead of calling observe again; screenshot only for missing or redacted evidence. Never reuse controlId/fieldId/decisionId from a prior session or restart: observe the saved tab once on resumption. Observe again only when the page was externally changed, is loading, lacks needed evidence, or a saved checkpoint is resumed. Execute a reviewed pending decision before requesting another; next/observe invalidate it.

Honor the job source's application mode: find_only means do not start an application, prepare means fill and save without submitting, and auto permits submission only when the candidate's global authorization is also submit. Follow applicationPolicy for reusable answers. autoFillKnown permits only facts already present in the profile, CV or saved answers. acceptPrivacy covers required application privacy/data-processing notices, not unrelated contracts or release agreements. When groupRecruitmentConsent is true, the candidate has also authorized transferring their application data (contact details, location, profile links, CV and compensation expectation) to the employer/recruiting system and its corporate group, and storing, processing and sharing it for recruitment for this and other positions in that group, including a recruitment talent pool. Accept those consent boxes without asking again, whether required or optional. This explicit policy takes precedence over generic ask-for-legal-agreement rules for those recruitment-data notices only. It does not permit marketing, unrelated third-party data sharing, commercial agreements or release agreements. A bundled box that also requires an out-of-scope permission is not covered. When false, do not infer group-wide consent from acceptPrivacy. Use the configured demographic and marketing defaults. For unknown important facts or new legal agreements, ask or skip according to policy; never invent a fact or declaration.
Claim a found listing with update_application(status=working). If the tool rejects ownership, leave it for the current owner or ask the user to take over the interrupted item in the app.
Fill fields only from the profile, CV and user answers. Use the candidate's compensation and availability rule; relative start dates use today's actual date. Honor the unchanged-CV preference. For cover letters read ../write-cover-letter/SKILL.md; save the exact text in documents/ before pasting or uploading it so the candidate can view it in the app.
Before asking, read ../candidate-profile/SKILL.md if not already in context and use the get_task_context result already read at task start; do not fetch it again. For missing-fact questions supply applicationBlocker.review with cvChecked and missingFacts (key, gap, knownValueGap if existing evidence is incomplete/conflicting). Resolve the field from the profile, CV and saved answers where the evidence actually supports it. Persist newly learned reusable facts with remember_candidate_fact and their source; keep job-specific decisions local. For facts still unknown in an open form, call ask_candidate with jobId and resumeContext: browser identity (including the profile/session if exposed), the observed stable tabId, current form url, step and nextAction. Never substitute a REPL variable or positional tab index for a stable ID. Save this context with save_application_checkpoint whenever changing the active application tab or leaving a form. Then mark blocked and report the bounded task blocked. Leave that tab open and unchanged; use a different tab for independent work. Never close, reload, navigate away from or reuse another application's unfinished tab. Retrieve replies and resumeContext with the single get_task_context call at the start of the next assigned task.
On return, reacquire the saved tab through the browser tool using its actual browser and tab identity, inspect a fresh snapshot and verify candidate account, company and role. Apply the saved answers at the recorded step. Do not open the listing again or restart the form while its tab exists. For older applications without a checkpoint, inspect existing tabs for the matching form first and save its checkpoint rather than opening a duplicate. If IDs changed, enumerate existing tabs and identify the correct application from fresh page evidence. If the original tab is gone or the site expired the form, inspect the saved draft and submission state via the verified listing; do not claim that unsaved form state survived or repeat an uncertain submission. Do not invent addresses, consent, legal declarations or experience.
When the form is ready, mark prepared with a concise summary of documents and answers. A research-only candidate must not reach this stage. If authorization is prepare, leave it ready for review. For submit authorization, check the profile authorization, source mode and saved consent in the task-start context; do not call get_task_context or get_candidate_profile again before submission. Reuse the most recent fresh form evidence unless missing, loading or changed. Mark submitting immediately before the external submit action, then perform it through the available tool under its own rules. Do not insert repeated activity announcements or another profile read between this check and submission; if evidence or authorization changes, stop dependent actions and honor the new information without another get_task_context call. An MCP status change does not submit a form.
After submission, inspect the explicit success page or confirmation message/email. Call record_submission with exact observed confirmation text, its source URL and the documents actually sent. Do not include secret URL tokens. This records reported evidence, not an independent verification by the app. record_submission also completes the matching active application/verification task in the same database transaction. If its result says completion.taskReported=true, end this turn with a brief user-facing result. Do not call update_application, report_campaign_work, report_activity or another browser tool afterward; submitted is terminal. If there is no matching task, retain the saved submission and follow the returned completion instruction.
If a click times out or success is unclear, mark uncertain. Inspect authoritative confirmation before any further action; never repeat submit simply because the first result was lost.
Any separately requested external bookkeeping belongs to a separate explicit task after success; do not add optional LinkedIn marking to the application-completion path. Send the direct listing link through a named notification channel only if explicitly authorized and its messaging tool is available. Close completed tabs after saving. Preserve incomplete forms with useful unsaved work and record the blocker.

Do not turn listing requirements into a candidate interview or require the user to verify fit. A requirement in a job description is not a required application-form field. Use the CV's actual technologies, role dates and descriptions without inflating them: Java work at one employer supports that work, not an invented level of expertise or years attributed to Java unless the dates substantiate them. An omitted technology is unknown, not proof of no experience. Fill the known application fields and submit the accurate unchanged CV within authorization. Leave unknown optional fields empty. Record fit concerns as notes; do not skip a score-qualified listing because of a separate suitability veto.
For job-specific ask_candidate calls, supply applicationBlocker with kind=required_form_field, access or uncovered_consent, evidence quoting the observed required field label/marker or access/consent blocker, and reasonUnknown explaining the specific gap after consulting the CV, profile and saved answers. Only ask that exact gap; do not append years/frameworks/production-experience questions unless the actual required form fields demand them. Check existing applicationPolicy before asking consent. This gate does not restrict initial candidate setup questions.

Automatic application mode is standing candidate authorization, not a request for another confirmation: if the current profile authorizes submit and the source allows auto, submit the completed accurate application without asking “Do you approve this application?” or creating an approval form. Review the settings from task-start context before submission and honor any explicit revocation, prepare/research modes, provider-required approvals and uncertain-submission verification. Use existing privacy/group-recruitment permissions without asking again. Uncovered consent questions must include applicationBlocker.consentScope; never disguise routine submission approval as an unknown form fact. Prompts describe the application's saved authority; do not impersonate the candidate or invent new first-person instructions.

## Recover field-entry failures before involving the candidate
A known email/phone disappearing is an automation failure, not a missing fact. Take a fresh snapshot; verify the visible editable field, candidate and form, inspect the validation message and required formatting. Try at most two distinct safe methods supported by your browser tools (for example clear/fill then blur, or focused keyboard typing then blur). Read the resulting value after each attempt. Preserve the existing tab and draft. Do not blindly loop, reload a draft, disable site protections, or resubmit an uncertain application.
Only if the failure persists and manual input can actually unblock it, ask for that minimal action with applicationBlocker.kind=access and recovery={kind:"form_entry",attempts:[{method,result},{method,result}],userActionReason}. Never ask the user to supply a contact detail already known just because typing failed. For login, MFA, tool-required confirmation or missing browser capability use recovery.kind=user_only and explain the observed requirement; do not pretend to have attempted unavailable tools. Site outages with no useful user action should be reported as technical blockers without a candidate question.

Before asking the candidate about CAPTCHA, inspect the current challenge with observe/screenshot and allow an automatic verification already in progress to settle briefly. If it clears, continue without asking. If the active browser tool permits solving it and exposes the required controls, attempt the visible challenge through normal UI using observed targets (including visual challenges only when that tool supports their interaction). Limit recovery to at most two attempts and 60 seconds total; verify the observed result after each. Do not invent unavailable actions, use arbitrary coordinates in Jev, bypass tool-required human handling, disable site protections, call external solver services, switch accounts, reload the draft, or repeat an uncertain submission. The CAPTCHA completion may itself finish submission: inspect confirmation before any further submit action.
If it still requires user action, ask only for the remaining challenge using applicationBlocker.kind=access and recovery={kind:"captcha",userActionReason,captchaCheck:{state:"required",capability:"supported",evidence:"fresh observed remaining challenge"},attempts:[{method,result}]}. If interaction is prohibited by the active tool, use capability="tool_disallowed"; if controls are not exposed (for example an inaccessible iframe), use capability="not_exposed". In either case give the specific limitation in captchaCheck.limitation and do not fabricate attempts or change tools to evade a restriction. CAPTCHA is a technical blocker, not missing CV information; this recovery does not require a CV review. Keep the existing draft/tab and checkpoint. Never ask while the observed challenge is already cleared.

Contact fields may be redacted or omitted by AX/DOM readouts even when visibly filled. An absent AX Value or empty read-only DOM value is NOT evidence that typing failed. Bring the field into view and inspect a fresh screenshot before retrying, and again before requesting manual input. If visible content is correct, continue; never erase a correct value to satisfy a masked readout. For manual form-entry requests supply recovery.visualCheck={method:"screenshot",result:"empty" or "invalid",evidence:"what is visibly wrong"}. Do not claim only a human can fill an input based on two masked programmatic reads. Read the browser's upload troubleshooting before escalating a file chooser failure.

Browser tab retention marks can be turn-scoped. Before EVERY turn ends, including source searches, re-mark all still-needed unfinished application tabs with markHandoff() when the browser API supports it. A saved checkpoint or a mark from a previous turn is not tab retention. Leave other pending forms open until answered and completed. When JobLoop requests recovery, re-enumerate the correct browser, recover a missing draft through the verified listing, check for prior submission, and update its checkpoint. Resolve a misleading technical question through resolve_technical_question with fresh evidence; never represent that as a candidate answer or consent.

## Keep submission completion short
Once required fields and consent are ready, use this bounded sequence: review the context already read at task start (no additional get_task_context call), prepared/submitting state transitions as needed, one reviewed submit action, inspect its returned observation for explicit success, then record_submission. Only request another observation when confirmation has not appeared or the result is uncertain. Do not treat Jev DONE or executed=true alone as success. Save checkpoints when leaving a draft or changing its tab, not repeatedly during an uninterrupted final submission sequence. Status transitions and the final proof record already update the application UI; do not add multiple “about to submit” activity calls. Never retry a submission to reduce calls.

## Explicit automatic consent settings
Read the current applicationPolicy before acting. legalAgreements=auto records the candidate's preference to automatically accept application-related agreements and release forms within the application's scope. marketing=auto records permission for marketing consent boxes; decline means reject and profile_only means use explicit saved preferences. Do not ask again solely for a preference already covered by these settings. These settings do not override the executing tool/provider's requirement for action-time confirmation; when required, use an observed access blocker through ask_candidate. They never supply missing factual declarations, create authorization for financial commitments, or authorize unrelated actions. unknownImportant remains ask or skip: never invent an unknown fact or sign an unsupported factual statement.
