description: Fill, resume and verify JobLoop applications through the assigned browser, using saved candidate facts and authorization without duplicate submissions.
---

When following the listing’s Apply link to an employer/ATS vacancy, call link_job_url with the saved jobId, observed destination URL and evidence of the link/redirect before filling or submitting. JobLoop extracts the identity; do not invent IDs or infer identity from a similar title. Honor the returned canonical job/duplicate guard: report the task done for an existing completed/owned vacancy; verify uncertain sends without resubmitting. Generic login/success pages are not vacancy identities. Jev also records known vacancy URLs from owned application tabs automatically. Save the current application checkpoint before update_application(submitting), so the final guard checks its destination.


# Apply to the assigned job

When task context contains `job.preparation`, reuse its exact saved documents and answers (paths are relative to `documentRoot`). Preserve user-edited content. Recheck the actual form, missing requirements and package freshness before sending; a package alone is not evidence the form is filled. Refresh affected content when candidate facts changed, retaining user edits and previously submitted versions. A preparation hold prohibits submission until the user separately queues Başvur.

Use this workflow for application and verification tasks. Read it once per conversation; reuse it while unchanged. Read a linked reference only for the condition described beside it.

## Start from the saved state

- Use the single `get_task_context` result for this task: profile, source mode, job, rankDecision, replies, reusableAnswers and checkpoint. Reuse it through questions and submission. A resumed task may refresh it once to receive new replies. Read bounded `list_applications` only for a necessary cross-job check.
- Process `candidateReplyActions` before browsing: explicit job-specific skip → `stop_application_followup`; explicit candidate-reported send → `record_candidate_submission`; already-unavailable required documents → `defer_missing_documents`. Use the returned questionId. A negative form answer, completed CAPTCHA or unclear “done” is not a cancellation or submission report. On `completion.taskReported=true`, end without further tools.
- Preserve `job.duplicateApplication` and uncertain/submitted outcomes. A different source URL, company suffix or unknown location does not establish another vacancy. Verify a prior uncertain send before ranking or form work. Repeat only when this exact task has `repeatUncertain=true`, the old attempt is archived in `priorSubmissionAttempts`, and the user explicitly accepted possible duplication. That exception permits one fresh attempt for this job, not other uncertain jobs or a second blind retry.
- When get_task_context.applicationAuthorization has mode=submit and scope=this_job, the user explicitly queued this job: apply directly without a scoring prerequisite or score/availability veto; check the actual site and record real closure if observed. Otherwise follow the saved rankDecision. Score only when no rank exists, using `../rank-jobs/SKILL.md`; reuse existing scores. Below-threshold jobs remain saved unless explicitly overridden. Do not add a separate suitability veto to an eligible job.
- In Jev, begin browser work with `resume_application(jobId)`. It claims found/blocked jobs as working and returns a full observation of the owned tab or exact saved listing. Do not repeat the working update. `verification_required` prohibits a replacement form or resubmission. For another browser backend, follow browserResume and the saved browser/profile; never migrate an unfinished draft or pass a numeric Chrome tabId to Jev.
- Verify candidate account, company and role. Respect ownership errors and preserve drafts. For login read [references/recovery-login.md](references/recovery-login.md); for a missing tab or unchanged blocker read [references/recovery-saved-tabs.md](references/recovery-saved-tabs.md). Read only the matching file when an actual obstacle occurs.

## Prepare supported answers once

Build a compact answer plan from the task context and CV: exact values, sources, formatting rules and unresolved facts. Read the unchanged CV once when needed; reuse it across fields and tasks for this candidate. Update affected answers when the candidate, document or evidence changes. Never infer citizenship, work permits, experience, qualifications or consent. Reusable answers retain their source and date; employer-specific answers stay local to this job.

Use the recorded salary and availability rules. Evaluate relative dates using today's date; do not invent an exact date when only a notice period is known. Honor the unchanged-CV preference. For a cover letter, read `../write-cover-letter/SKILL.md` and save the exact document in `documents/` before using it.

A listing requirement is not a missing application-form fact. Record fit concerns without interviewing the candidate about suitability. Leave unknown optional fields empty. Before asking about genuinely missing information, read `../candidate-profile/SKILL.md` if needed and resolve everything supported by the existing profile, CV and saved answers.

## Fill and inspect

Use the fresh observation returned by each browser action as the next state. Do not add `observe` after a verified fill, selection, click or upload just to repeat it. Read again when the page is loading, external changes occurred or evidence is missing. A selected filename alone does not prove server acceptance; follow the displayed upload status.

For Jev: When `controlMaps=replace`, controls/clickTargets/fillFields/scrollTargets are complete CURRENT lists: discard older maps. No base observation is required for IDs. `observationMode=compact` omits duplicate elements and unchanged prose; `textUnchanged=true` is not fresh submission evidence. Do not request missing_baseline; current maps already stand alone. Only request fullReason=context_loss if page prose was actually lost. The merge rules below apply only to legacy mapDeltas=true responses.

- Batch known ordinary text answers with `browser_jev_fill_fields` using current fieldIds. Inspect each result: filled/unchanged is verified, not_attempted is untouched, uncertain requires inspection. Correct only unresolved fields.
- Use `browser_jev_click` for an exact authorized clickTarget. Use next → act only when the target is unclear; review its proposed action and supply exact verified text yourself.
- Button-driven custom lists marked `autocomplete:true` also use `browser_jev_list_suggestions` and `browser_jev_autocomplete`; omit `text` because these are not editable inputs. Match the exact returned option label.
- Native select: read unknown options once with `browser_jev_list_options`, then use `browser_jev_select_option`. Reuse `optionsRead.complete` lists. Autocomplete: use actual `browser_jev_list_suggestions` labels and `browser_jev_autocomplete`; do not guess translated labels or internal enums.
- For `controls.choice`, match both question and option, then use `browser_jev_select_choice`. Selection tools reveal their targets automatically. `selection.verified` / `controlState.verified` is evidence; ready/executed/progress alone is not. An unresolved selection must be checked before submission.
- Execute browser calls on a tab in order; one call can invalidate handles needed by another. Copy complete IDs exactly. Merge delta controls/scrollTargets by controlId, clickTargets by targetId and fillFields by fieldId; delete IDs in the corresponding removedControls/removedScrollTargets/removedClickTargets/removedFillFields arrays. Omitted entries are unchanged. An empty delta `controls:[]` does not mean the form has no controls; retain earlier controls unless their IDs appear in `removedControls`. Apply these extended map deltas only when mapDeltas=true; older servers without this flag replace clickTargets, scrollTargets and fillFields completely. Used click/fill IDs are consumed; uploads replaces its map each time. `browser_jev_observe` reads fresh changes by default. Use `full:true, fullReason:"context_loss"` after compaction, or `fullReason:"missing_baseline"` when the base observation is unavailable. Routine verification uses deltas, never full just to confirm a click or submission. Fresh confirmation text in an action result is sufficient; observe again only when the result is still loading or lacks evidence. New sessions require new handles.
- Use reveal for a known offscreen control and scroll for its observed container. Choice failures return a full observation and a reason: `control_changed`/`unknown_control` require fresh IDs; `target_not_visible`/`reveal_failed`/`no_safe_click_point` mean the control exists but cannot currently be clicked safely. Do not describe these as missing fields. On stale, use returned updates; on no_progress, do not repeat the unchanged failed action. Never guess selectors/coordinates or click through overlays.

Before questions or submission, inspect all accessible required fields and consent, including below the fold, with `browser_jev_inspect_form` or the active browser's equivalent. Repeat only after meaningful form changes. `required=null` is unknown, not optional. Never submit merely to discover missing fields.

For required portal signup/login or emailed verification codes, read [references/portal-accounts.md](references/portal-accounts.md). Use the secure password tool, never a chat password question.

## Authorization and questions

When get_task_context.applicationAuthorization.mode=verify, only check the existing submission result and record observed confirmation. Do not prepare a new form, resubmit, or complete a sending step. Recording fresh field validation that prevented submission completes this verification task. If the outcome remains unknown, preserve uncertain and report the actual blocker.

An explicit get_task_context.applicationAuthorization (mode=submit, scope=this_job) authorizes this specific application even when the profile is research/prepare, the source is find_only/prepare, ranking is missing or below threshold, or the campaign target is reached. It grants no new candidate facts or privacy/legal consent, and never authorizes duplicate submission. Otherwise follow candidate authorization and source mode: research/find_only permits research; prepare permits a saved draft; submission requires both candidate submit and source auto. Existing automatic authorization needs no new “may I submit?” question. Honor revocation and the executing tool's confirmation rules.

Use applicationPolicy for known-field filling, recruitment privacy, group recruitment, demographics, marketing and legal agreements. Before an agreement or consent whose scope is unclear, read [references/consent.md](references/consent.md). Never invent factual declarations or silently extend permission.

Before the first candidate question read [references/questions.md](references/questions.md) for detailed validation and recovery requirements. Ask only for an observed required field, unresolved access barrier or uncovered consent. Quote evidence and explain the exact unknown in `applicationBlocker`. For missing facts provide `review={cvChecked,missingFacts:[{key,gap,knownValueGap?}]}`; technical access blockers do not require a CV review. Gather all currently missing required facts/consents in one request of up to 10 fields. Give each a concise Turkish label; tag reusable facts with factKey and consent with consentScope. Reuse an unanswered question; persist newly learned reusable facts with `remember_candidate_fact` and their source.

`ask_candidate` receives jobId and the actual resumeContext (browser/profile, stable tabId, URL, step, nextAction). It saves the checkpoint, blocked/uncertain state and task report together. On `completion.taskReported=true`, end immediately. Do not separately save/update/report the same question. A prior blocker needs new evidence or a relevant reply before refilling; see the recovery reference.

## Submit and finish

1. Review the current answer plan, required fields, evidence and authorization already in context.
2. Mark prepared with the documents and answers. Never click the final submit target until update_application(submitting) has succeeded; do not postpone these state updates until after the click. In prepare mode leave the draft for review. Otherwise mark submitting immediately before one authorized external submit action. A status update is not a submission.
If a click returns `submission_not_started`, no click was dispatched: do not call the button unresponsive or retry via next/act. Reconcile the form state (empty delta maps are not missing fields), complete and verify required fields, then persist prepared/submitting before the authorized send. Never mark prepared merely to bypass the guard.
3. Inspect the action's returned page for explicit confirmation. Request another observation only for loading or missing/uncertain evidence. DONE and executed=true are not proof.
4. Call `record_submission` with observed text, its source URL (no secret tokens) and documents actually sent. Use kind=already_submitted directly when the authenticated site shows this exact candidate/vacancy was previously applied to; no synthetic state transitions or repeated send.
5. On `completion.taskReported=true`, end with a brief result. No further browser, activity, update or report call. Otherwise follow the returned completion instruction.

After a send without confirmation, record uncertain and inspect the existing outcome. Do not retry Submit or reset it to working/blocked. For explicit field validation read [references/recovery-validation.md](references/recovery-validation.md); for a pending verification step read [references/recovery-verification.md](references/recovery-verification.md). Load only the applicable file.

Save checkpoints when changing tabs or leaving drafts. Keep incomplete applications in their own tabs; never reload, navigate away from or reuse another job's unfinished form. Refresh turn-scoped markHandoff when supported, even on search turns. Jev closes completed owned tabs automatically. Optional bookkeeping or notifications require a separate explicit task/authorization.

`browser_wait` is a stop condition: end without questions, status changes or report_campaign_work; the app reconnects and resumes the same task. For other task outcomes call report_campaign_work for the current task ID: done only for recorded proof, an explicit skip or an authorized prepared draft; otherwise blocked with evidence. Technical blockers with no useful candidate action use blocker={kind:technical,requiresUserInput:false,evidence,reason}. Correct rejected reporting on this same task. Technical failures with no useful user action are reported with evidence, without asking the candidate to fix them.

Describe a submission as completed only after recorded success evidence. Clicking Submit followed by CAPTCHA means “gönder düğmesine basıldı, doğrulama bekliyor”, never “gönderildi”. Do not ask the candidate to submit the entire application merely because one ordinary field could not be filled; ask only for the blocked field, then inspect and finish within current authorization.

Tab hygiene: keep one current continuation tab per application. After the employer form opens in a child tab, save that exact form checkpoint; Jev prunes only empty owned listing ancestors. Keep filled drafts and pending authentication/verification tabs until resolved. Once submission is confirmed, completed job tabs are cleaned automatically. For other browser backends close only your own finished listing/intermediate tabs after verifying the live continuation form, and your completed application tabs after proof is saved. Never close user-owned tabs or reuse another application's draft. Manually closed tabs are not live checkpoints; verify existence before resuming and never reopen/retry an uncertain send.

## Candidate location and embedded forms
- Personal information fields such as City, Address and Current location mean the candidate's residence. Use profile.location or explicit saved residence evidence, never the job's city. A job in Regensburg does not make the candidate live there. For preferred office / job location use only the candidate's stated preference; ask only when genuinely unknown.
- For embedded forms use `embeddedForms` with `browser_jev_frame_observe` and `browser_jev_frame_act` in place before declaring manual work necessary. Preserve the parent context; do not reopen a nested frame URL or an uncertain submission.
- Autocomplete IDs and options may live in shadow DOM. Read the complete associated suggestions, select the exact verified residence option, and verify acceptance; do not replace a failed selection with the posting city. For hidden native checkboxes/radios use the observed control/label action, verifying checked state. Do not ask the user to finish the whole application because one known field is inaccessible.

Recovery evidence: `submission_not_started` / `blockerOrigin=jobloop_submission_guard` means JobLoop prevented dispatch, not that the website ignored a click. Report the actual tool-side blocker; never attribute it to the site. For `rejectedControlId`, discard that ID and use the returned `availableTargets` matching the question and recommended tool. Never repeat it after `no_progress`; never select a different question merely because its option looks familiar. Hidden/inactive upload fields are not actionable; open the actual form before uploading.

Native date fields: use browser_jev_fill_fields with type=date fieldId and ISO YYYY-MM-DD (for example 2026-11-28), even when the page displays dd.mm.yyyy. Respect min/max. Determine the answer from verified availability/notice-period facts; do not invent a date or ask the candidate to manually fill a supported date control. Reveal an offscreen date field first and verify the returned value/validity.

Cookie consent inside an about:srcdoc iframe appears in clickTargets with context="Cookie consent iframe". Use browser_jev_click on its exact targetId in the same tab according to the candidate consent settings; do not try opening about:srcdoc in another tab or ask for manual completion solely because the outer page has no controls. Inspect the returned page for the banner closing; executed=true alone is not confirmation.

Nested application frames (e.g. iCIMS): use embeddedForms frameId with browser_jev_frame_observe, then browser_jev_frame_act on its scoped targets. Prefer hasForm=true entries. This operates in place and preserves the parent/session context; opening the frame URL in another tab can recreate the outer shell. Do not repeat that workaround. Native text/date fields, checkbox/radio choices, select options and buttons are supported; follow current consent/submission rules. For upload popups, use uploads even if ordinary clickTargets is empty; an aria-labelledby-bound file input may be the only actionable control.

Custom iframe dropdowns: click the observed combobox target to open it, then choose an exact visible option from the returned controls. If a search input appears, fill it with the known answer and use the resulting visible option. Never assign a hidden backing select or invent options. Top-level `uploads` also discovers usable iframe file inputs; use those IDs instead of opening the system file chooser. After CV import, verify that the site did not overwrite previously entered profile fields.
File upload labels such as “Attach” can be ambiguous. Match each upload to its surrounding section before choosing a file. Put the CV only in Resume/CV fields and an actual cover letter only in Cover Letter fields; leave an optional Cover Letter empty when no suitable letter exists. Verify filenames in their respective sections after upload.
Follow the field's own formatting hint even when HTML validity reports true. For a separate country code selector plus a phone field marked “digits only (0-9)”, enter the verified local number without spaces, punctuation, or a repeated country prefix; confirm that the final Submit button becomes enabled before treating the form as ready.

For an embedded input with `aria-autocomplete=list`, frame_act fill returns `needs_selection` without blurring. Use the fresh returned visible option target and frame_act click exactly once. Inspect the selected city afterward; typed text alone is not a chosen location.

If Submit is disabled or absent from clickTargets, call inspect_form and check `submitControls` plus `missingRequired`. Fill the current missing fields using fresh targets, then verify again. `required=null` still needs human review; a disabled submit is not proof of a browser-control failure.
