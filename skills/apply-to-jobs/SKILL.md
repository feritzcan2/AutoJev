---
name: apply-to-jobs
description: Fill and submit suitable JobLoop applications through available browser tools, track progress and verify submission without duplicates.
---
Read get_task_context immediately before working on an application; it includes the current profile, job, source, saved replies and checkpoint. Request full list_applications only when other history is needed. Confirm the browser is signed into the correct candidate account. Never submit an existing submitted or uncertain application again.
Honor the job source's application mode: find_only means do not start an application, prepare means fill and save without submitting, and auto permits submission only when the candidate's global authorization is also submit. Follow applicationPolicy for reusable answers. autoFillKnown permits only facts already present in the profile, CV or saved answers. acceptPrivacy covers required application privacy/data-processing notices, not unrelated contracts or release agreements. When groupRecruitmentConsent is true, the candidate has also authorized transferring their application data (contact details, location, profile links, CV and compensation expectation) to the employer/recruiting system and its corporate group, and storing, processing and sharing it for recruitment for this and other positions in that group, including a recruitment talent pool. Accept those consent boxes without asking again, whether required or optional. This explicit policy takes precedence over generic ask-for-legal-agreement rules for those recruitment-data notices only. It does not permit marketing, unrelated third-party data sharing, commercial agreements or release agreements. A bundled box that also requires an out-of-scope permission is not covered. When false, do not infer group-wide consent from acceptPrivacy. Use the configured demographic and marketing defaults. For unknown important facts or new legal agreements, ask or skip according to policy; never invent a fact or declaration.
Claim a found listing with update_application(status=working). If the tool rejects ownership, leave it for the current owner or ask the user to take over the interrupted item in the app.
Fill fields only from the profile, CV and user answers. Use the candidate's compensation and availability rule; relative start dates use today's actual date. Honor the unchanged-CV preference. For cover letters read ../write-cover-letter/SKILL.md; save the exact text in documents/ before pasting or uploading it so the candidate can view it in the app.
Before asking, read ../candidate-profile/SKILL.md if not already in context and refresh get_task_context. Supply applicationBlocker.review with cvChecked and missingFacts (key, gap, knownValueGap if existing evidence is incomplete/conflicting). Resolve the field from the profile, CV and saved answers where the evidence actually supports it. Persist newly learned reusable facts with remember_candidate_fact and their source; keep job-specific decisions local. For facts still unknown in an open form, call ask_candidate with jobId and resumeContext: browser identity (including the profile/session if exposed), the observed stable tabId, current form url, step and nextAction. Never substitute a REPL variable or positional tab index for a stable ID. Save this context with save_application_checkpoint whenever changing the active application tab or leaving a form. Then mark blocked and report the bounded task blocked. Leave that tab open and unchanged; use a different tab for independent work. Never close, reload, navigate away from or reuse another application's unfinished tab. Retrieve replies and resumeContext with get_task_context.
On return, reacquire the saved tab through the browser tool using its actual browser and tab identity, inspect a fresh snapshot and verify candidate account, company and role. Apply the saved answers at the recorded step. Do not open the listing again or restart the form while its tab exists. For older applications without a checkpoint, inspect existing tabs for the matching form first and save its checkpoint rather than opening a duplicate. If IDs changed, enumerate existing tabs and identify the correct application from fresh page evidence. If the original tab is gone or the site expired the form, inspect the saved draft and submission state via the verified listing; do not claim that unsaved form state survived or repeat an uncertain submission. Do not invent addresses, consent, legal declarations or experience.
When the form is ready, mark prepared with a concise summary of documents and answers. A research-only candidate must not reach this stage. If authorization is prepare, leave it ready for review. For submit authorization, re-read the profile, mark submitting immediately before the external submit action, then perform it through the available tool under its own rules. An MCP status change does not submit a form.
After submission, inspect the explicit success page or confirmation message/email. Call record_submission with exact observed confirmation text, its source URL and the documents actually sent. Do not include secret URL tokens. This records reported evidence, not an independent verification by the app.
If a click times out or success is unclear, mark uncertain. Inspect authoritative confirmation before any further action; never repeat submit simply because the first result was lost.
Only after recording success, mark the external listing applied on LinkedIn if appropriate and authorized. Send the direct listing link through a named notification channel only if explicitly authorized and its messaging tool is available. Close completed tabs after saving. Preserve incomplete forms with useful unsaved work and record the blocker.

Do not turn listing requirements into a candidate interview or require the user to verify fit. A requirement in a job description is not a required application-form field. Use the CV's actual technologies, role dates and descriptions without inflating them: Java work at one employer supports that work, not an invented level of expertise or years attributed to Java unless the dates substantiate them. An omitted technology is unknown, not proof of no experience. Fill the known application fields and submit the accurate unchanged CV within authorization. Leave unknown optional fields empty. If existing evidence shows the role is unsuitable, record the reason instead of interviewing the candidate to rescue the match.
For job-specific ask_candidate calls, supply applicationBlocker with kind=required_form_field, access or uncovered_consent, evidence quoting the observed required field label/marker or access/consent blocker, and reasonUnknown explaining the specific gap after consulting the CV, profile and saved answers. Only ask that exact gap; do not append years/frameworks/production-experience questions unless the actual required form fields demand them. Check existing applicationPolicy before asking consent. This gate does not restrict initial candidate setup questions.

Automatic application mode is standing candidate authorization, not a request for another confirmation: if the current profile authorizes submit and the source allows auto, submit the completed accurate application without asking “Do you approve this application?” or creating an approval form. Re-read settings before submission and honor revocation, prepare/research modes, provider-required approvals and uncertain-submission verification. Use existing privacy/group-recruitment permissions without asking again. Uncovered consent questions must include applicationBlocker.consentScope; never disguise routine submission approval as an unknown form fact. Prompts describe the application's saved authority; do not impersonate the candidate or invent new first-person instructions.

## Recover field-entry failures before involving the candidate
A known email/phone disappearing is an automation failure, not a missing fact. Take a fresh snapshot; verify the visible editable field, candidate and form, inspect the validation message and required formatting. Try at most two distinct safe methods supported by your browser tools (for example clear/fill then blur, or focused keyboard typing then blur). Read the resulting value after each attempt. Preserve the existing tab and draft. Do not blindly loop, reload a draft, disable site protections, or resubmit an uncertain application.
Only if the failure persists and manual input can actually unblock it, ask for that minimal action with applicationBlocker.kind=access and recovery={kind:"form_entry",attempts:[{method,result},{method,result}],userActionReason}. Never ask the user to supply a contact detail already known just because typing failed. For login, MFA, CAPTCHA, tool-required confirmation or missing browser capability use recovery.kind=user_only and explain the observed requirement; do not pretend to have attempted unavailable tools. Site outages with no useful user action should be reported as technical blockers without a candidate question.

Contact fields may be redacted or omitted by AX/DOM readouts even when visibly filled. An absent AX Value or empty read-only DOM value is NOT evidence that typing failed. Bring the field into view and inspect a fresh screenshot before retrying, and again before requesting manual input. If visible content is correct, continue; never erase a correct value to satisfy a masked readout. For manual form-entry requests supply recovery.visualCheck={method:"screenshot",result:"empty" or "invalid",evidence:"what is visibly wrong"}. Do not claim only a human can fill an input based on two masked programmatic reads. Read the browser's upload troubleshooting before escalating a file chooser failure.

Browser tab retention marks can be turn-scoped. Before EVERY turn ends, including source searches, re-mark all still-needed unfinished application tabs with markHandoff() when the browser API supports it. A saved checkpoint or a mark from a previous turn is not tab retention. Leave other pending forms open until answered and completed. When JobLoop requests recovery, re-enumerate the correct browser, recover a missing draft through the verified listing, check for prior submission, and update its checkpoint. Resolve a misleading technical question through resolve_technical_question with fresh evidence; never represent that as a candidate answer or consent.
