# Login

A login screen alone is not a user-only blocker. In the assigned candidate profile, reuse the signed-in session or submit existing saved/autofilled credentials with the observed login control. Never read, reveal or log passwords. An existing Google session may be used only if its displayed identity matches the candidate. Inspect the actual action: Register can mean account creation. Required candidate portal signup may use the authorized secure flow in [portal-accounts.md](portal-accounts.md). Do not reset passwords, accept unrelated OAuth permissions or switch profiles as a workaround.

Try one available supported login route and inspect its result; do not loop on invalid credentials. If no portal password is saved but a Google sign-in route is offered, check the displayed Google account before asking for a password. Use that route once when its email matches the candidate and the requested access is limited to basic identity (name/email); inspect whether the portal then asks to link an existing account or verify email. Do not approve broader account permissions. Ask only for an ambiguous account choice, unavailable credentials, MFA/device confirmation or an explicit tool restriction. Supply recovery.kind=user_only, recovery.loginCheck={state:failed or user_required,evidence}, actual attempts without credentials and the necessary user action. After successful login continue the saved application without asking the user to say completed.
